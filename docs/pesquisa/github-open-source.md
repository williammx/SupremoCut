# Pesquisa GitHub: funcionalidades transplantáveis de editores de vídeo open source

Pesquisa feita em 2026-08-30 pelo agente PESQUISADOR da FORJA, em fan-out. Alvo de calibração: **SupremoCut**, editor de vídeo local para Windows em Remotion 4.0.517 + React 19 (composição em código React), `@remotion/player` para preview, Vite, timeline React própria, servidor Express local, motor Python (FFmpeg + faster-whisper + ElevenLabs), formato principal vertical 9:16 para anúncios/Reels/TikTok, usuário final leigo em programação.

Este documento é o mergulho técnico profundo na lista curada de repositórios pedida na missão (NLEs desktop, ferramentas Python/IA, e o ecossistema React/Remotion), mais uma rodada de descoberta ativa. Existe um documento irmão em `docs/pesquisa/editores.md`, feito em pesquisa anterior, com escopo mais amplo (inclui produtos comerciais como CapCut/Submagic/Opus Clip/Descript/Veed e outros projetos web como ClippyMe/Vanta) — os dois se complementam; este aqui é mais técnico e mais ancorado em código-fonte/documentação de arquitetura.

**Método:** toda afirmação abaixo vem de conteúdo real lido via `WebSearch`/`web_fetch` nesta tarefa (README, documentação oficial, wiki, código-fonte, changelog, fórum oficial), com o link exato citado. Onde uma fonte não pôde ser aberta diretamente e a informação veio só de um resumo de busca, isso está marcado explicitamente. Onde um repositório não pôde ser acessado ou não existe, isso está declarado em vez de chutado.

## Projetos estudados

### NLEs desktop (C++/Qt)

1. **OpenShot** — https://github.com/OpenShot/openshot-qt — editor de vídeo desktop Python/Qt (motor em C++ separado, libopenshot), GPLv3, explicitamente voltado a ser simples para iniciantes. Fontes lidas: README, `openshot.org` user guide (animation.html, clips.html), wiki de release notes v2.6.0, blog oficial de 2026 sobre proxy.
2. **Kdenlive** — https://invent.kde.org/multimedia/kdenlive (repo canônico, GitLab/KDE) — NLE profissional maduro do ecossistema KDE, construído sobre o MLT Framework, GPLv3. O navegador de arquivos do GitLab é pesado em JS; usei o mirror https://github.com/KDE/kdenlive via `raw.githubusercontent.com` para ler arquivos brutos, e https://docs.kdenlive.org para a documentação de usuário.
3. **Shotcut** — https://github.com/mltframework/shotcut — editor Qt6 mantido pela mesma equipe do MLT (Meltytech/Dan Dennedy), GPLv3, com "timeline nativa" (edita direto os formatos suportados por FFmpeg). Fontes: README, fórum oficial (`forum.shotcut.org`), blog de release, `shotcut.org/howtos/keyboard-shortcuts`.
4. **MLT Framework** — https://github.com/mltframework/mlt — motor em C (LGPL) de composição multitrack, usado por baixo do Shotcut e do Kdenlive. Fontes: `mltframework.org/docs/mltxml/` e `/docs/propertyanimation/`.
5. **Olive Video Editor** — https://github.com/olive-editor/olive — NLE em C++/Qt com compositing baseado em grafo de nós e color management via OpenColorIO. **Status do projeto:** o site oficial (`olivevideoeditor.org`) hoje só mostra "Olive will return..."; desenvolvimento praticamente parado desde 2023/2024 segundo buscas (existe um fork comunitário "Oak" não verificado diretamente). Fontes diretas: wiki de nós, código-fonte real de `keyframe.h`, wiki de formato de arquivo antigo.

### Python / linha de comando / IA

6. **MoviePy** — https://github.com/Zulko/moviepy — biblioteca Python de edição de vídeo programática (composição não-linear via numpy + FFmpeg). Fontes: README, referência de API v2.0 (`zulko.github.io/moviepy/reference`), guia de migração v2.0, issues públicas sobre memória/performance.
7. **auto-editor** — https://github.com/WyattBlue/auto-editor (site: `auto-editor.com`) — CLI de corte automático de silêncio/imobilidade, licença Unlicense (domínio público). Fontes: README e a documentação completa (`/ref/edit`, `/docs/v1`, `/docs/subcommands/*`, `/docs/actions`, `/docs/cookbook`, `/docs/transition`).
8. **m1k1o/clip — REPOSITÓRIO NÃO EXISTE.** Confirmado por 4 vias independentes: fetch direto (vazio, consistente com 404), API REST do GitHub (vazio), e principalmente a API de busca do GitHub (`/search/repositories?q=user:m1k1o+clip` → `"total_count":0`, prova conclusiva), e WebSearch (só retorna o modelo de IA CLIP da OpenAI, de outros autores, nada de m1k1o). Os repositórios reais de m1k1o são `neko` e `chat`, nenhum sobre edição de vídeo.
9. **OpenAI Whisper** — https://github.com/openai/whisper — modelo de ASR multitarefa (transcrição/tradução/detecção de idioma). Fontes: README, `model-card.md`, guia de timestamps por palavra.
10. **WhisperX** — https://github.com/m-bain/whisperX — pipeline que envolve o Whisper (via faster-whisper) com forced alignment por fonema (wav2vec2), batching por VAD, e diarização via pyannote-audio. Fonte: README completo.
11. **PySceneDetect** — https://github.com/Breakthrough/PySceneDetect (site: `scenedetect.com`) — biblioteca/CLI de detecção de corte de plano, múltiplos algoritmos. Fontes: README, `/features/`, `/docs/latest/cli.html`, `/docs/latest/api/detectors.html`.

### Ecossistema React/Web (o mais próximo do stack do SupremoCut)

12. **Remotion + ecossistema `@remotion/*`** — https://github.com/remotion-dev/remotion — o próprio framework que o SupremoCut usa. Mais de 30 páginas oficiais de `remotion.dev/docs` lidas diretamente, mais o README do monorepo e o `llms.txt` oficial.

Fontes: código-fonte real via `raw.githubusercontent.com`/`unpkg.com` (a documentação em `zdarcy.com` é renderizada em JS e não pôde ser lida via fetch de texto).
15. **designcombo/react-video-editor** — https://github.com/designcombo/react-video-editor — SDK/app comercial de edição em React sobre Remotion. Fontes: `package.json` real do repo, `designcombo.dev/framework/*`, `CHANGELOG.md`.

## Tabela consolidada de funcionalidades

Legenda de esforço: **P** = pequeno (horas a ~1 dia, sem dependência nova) · **M** = médio (dias, mudança de escopo moderada ou 1 dependência nova leve) · **G** = grande (semanas, nova infraestrutura ou dependência pesada).

### A. Arquitetura de dados da timeline

| Funcionalidade | Origem | O que faz | Por que importa aqui | Como implementar no nosso stack | Esforço |
|---|---|---|---|---|---|
| Clipe = lista de propriedades tipadas, maioria "key-frameable" | OpenShot (openshot.org/.../clips.html) | Cada clipe guarda Alpha, Location X/Y, Scale, Rotation, Shear, Volume, Time (curva de retime) etc., quase tudo como curva em vez de escalar fixo | Modelo mais simples de replicar que grafo de nós, mapeia quase 1:1 com props de componente React | Objeto `transform` no schema do clipe com campos `number \| Keyframe[]` + `resolveProp(prop, frame)` central | M |
| `sourceIn/sourceOut` separado de posição-na-timeline | MLT (mltframework.org/docs/mltxml) | in/out são absolutos ao arquivo fonte, nunca à timeline | Evita recalcular cortes ao mover um clipe | Auditar/garantir que o schema de clipe do SupremoCut já mantém os dois pares de campos sempre separados | P |
| Metadado de app nunca duplica dado do motor | Kdenlive (dev-docs/fileformat.md) | `.kdenlive` = XML MLT puro + propriedades `kdenlive:` penduradas nos mesmos objetos, nunca uma cópia paralela | Facilita migração de schema (Kdenlive documenta 5 gerações de formato) | Separar no JSON de projeto um objeto `meta` (nome, cor, grupo) do objeto `render` que o motor realmente consome | M |
| Transição como entidade própria (não pertence a nenhum clipe) | Kdenlive + designcombo | Transição referencia 2 índices/ids de track/clipe, existe como objeto à parte | Evita ambiguidade ao editar um dos lados isoladamente | `{id, kind, duration, fromClipId, toClipId}` como registro próprio no schema | P |
| Estado normalizado (ids + mapas, não árvore aninhada) | designcombo (`{tracks, trackItemIds, trackItemsMap}`) | Edição de um clipe único vira O(1); undo/redo granular fica mais simples | Performance e robustez em projetos com muitos clipes/overlays | Migrar o estado da timeline para padrão tipo-Redux (lista de ids + mapa id→objeto) | M-G |
| Campo `accepts` por trilha | designcombo (`ITrack{accepts?}`) | Restringe que tipo de item cada trilha aceita | Validação no próprio drag-and-drop (ex: trilha de legenda só aceita legenda) | Campo `accepts: string[]` no modelo de track | P |
| `groupId` com corte/efeito sincronizado | Kdenlive (grouping) | Cortar um clipe de vídeo agrupado com seu áudio corta o parceiro no mesmo ponto; "aplicar efeito a todo o grupo" propaga valor | Aplicável direto pois o SupremoCut já separa trilha de áudio | Campo `groupId` opcional; operações de corte/mover/editar propriedade replicam para todos os membros do grupo | M |
| `parentClipId` (parenting em vez de agrupamento) | OpenShot (Parent property) | Filho herda/segue transform do pai; usado para "grudar" gráfico em objeto rastreado | Base para overlay que segue produto/rosto em movimento | Campo `parentClipId`; compor matrizes 2D pai+filho antes de passar props ao componente Remotion | M |
| Sequência aninhada como "clipe" reutilizável | Olive (nesting, wiki de formato antigo) | Uma composição inteira usada como um clipe dentro de outro projeto | Permite salvar intro/outro de marca como bloco reutilizável | Trivial no Remotion — uma composição já é um componente React importável como filho | P-M |
| "Merge fields" / templates com placeholders | Shotstack Studio SDK (`{{ TITLE }}`) | Preenche um template programaticamente antes de renderizar | Base de uma futura feature de "templates de anúncio reutilizáveis" | Schema de composição com campos nomeados substituíveis, resolvidos antes de virar props do Remotion | M |

### B. Keyframes e animação

| Funcionalidade | Origem | O que faz | Por que importa aqui | Como implementar no nosso stack | Esforço |
|---|---|---|---|---|---|
| 3 modos de interpolação com ícone distinto na régua (bezier/linear/constant) | OpenShot (user guide animation.html) | Leitura visual instantânea do tipo de curva aplicada a cada keyframe | UX comprovada para o tipo de animação (zoom/pan/fade) que domina anúncio vertical | Mapeia quase 1:1 com `interpolate()` + `Easing` do Remotion; desenhar os 3 ícones na régua do clipe | M |
| Keyframes "simples" (2 pontos) vs. "avançados" (N pontos) como modos progressivos | Shotcut (fórum oficial) | Simple cobre só entrada/saída (anima "pra dentro"/"pra fora"); Advanced é uma curva completa | Complexidade progressiva certa para usuário leigo — cobre o caso comum sem expor curva completa | Modo "básico" padrão (2 controles: valor de entrada/saída) + botão "Avançado" que revela o editor completo | M |
| Interpolação por segmento, não curva global | Etro (`KeyFrame.evaluate()`, código-fonte) | Cada par de keyframes pode ter sua própria função de interpolação | Modelo simples e leigo-friendly, evita graph editor completo | `avaliarComKeyframes(pontos, frame)` com `easingId` por segmento; reimplementar em paralelo no motor Python p/ paridade preview/export | M |
| Tempo relativo ao fim do clipe | MLT (Property Animation API, `-1=220`) | Keyframe ancorado a "N frames antes do fim", não a um frame absoluto | Legenda/CTA que sempre sai perto do fim mesmo se o clipe mudar de duração depois | Suportar `{relativeToEnd: n}` como forma alternativa de âncora de frame no keyframe | P |
| Mistura de tipos de interpolação na mesma curva | MLT (Property Animation API) | Um clipe pode ter trecho discreto, depois linear, depois suave, na mesma propriedade | Flexibilidade que qualquer editor sério de keyframes precisa | Cada ponto carrega seu próprio tipo de interpolação (natural se já modelado por segmento, ver item acima) | P |
| Overshoot indesejado em spline automática — lição preventiva | Kdenlive + Shotcut (docs oficiais e blog de release, ambos documentam e corrigem) | Interpolação "Smooth"/Catmull-Rom pode ultrapassar o valor pretendido com 3+ keyframes em platô | Confirma que bezier com handles explícitos (o que o Remotion já favorece) evita a armadilha que dois motores independentes documentaram | Nenhuma ação — manter `Easing`/bezier explícito do Remotion, não implementar spline automática tipo Catmull-Rom | P |
| Tempo como fração exata, não float | Olive (`keyframe.h`, tipo `rational`) | Evita erro de arredondamento acumulado em fps não-redondos (29.97fps) | Já resolvido pelo Remotion (trabalha nativamente em frames inteiros) | Auditoria: garantir que todo cálculo de keyframe usa `frame` inteiro, nunca segundos em float | P |
| Clamp de handle bezier contra curva auto-intersectante | Olive (`keyframe.h`, `valid_bezier_control_in/out()`) | Limita matematicamente o handle arrastado para impedir 2 valores Y no mesmo X | Robustez, evita bug visual de "animação voltando no tempo" | Só relevante se o SupremoCut expuser edição fina de handle bezier no futuro | P |
| Copiar/colar keyframes entre clipes/efeitos | Kdenlive (docs, "Exchanging Keyframes") | Move uma animação inteira de um efeito/clipe para outro via clipboard | Reaproveitar um "zoom de entrada" já ajustado sem refazer manualmente | Keyframes já são JSON serializável — clipboard interno na timeline + colar com offset de frame | P |
| Snap em keyframes de outros clipes | Olive (achado via WebSearch sobre snapping) | Clipe/playhead gruda também em posições de keyframe de outros elementos, não só bordas/marcadores | Detalhe fino que nem OpenShot nem Kdenlive documentam — sincronizar corte com mudança de estilo de legenda | Incluir frames-com-keyframe como pontos de imantação no sistema de snapping já existente | P |
| Time curve avançada (congelar/reverso/slow-fast como curva) | OpenShot (Time property) + Kdenlive (Time Remap) | Generaliza "congelar quadro" (já existente) para reverso e rampas de velocidade | Slow-mo e speed ramp são pedidos constantes em Reels/anúncio "cinematic" | `interpolate()` mapeando frame-de-composição → frame-de-origem do `<Video>`/`<OffthreadVideo>` | M-G |
| Transform tool interativo (handles no preview) | OpenShot (user guide clips.html) | Arrastar cantos/centro/fora-das-linhas escala/move/rotaciona direto sobre o preview, sem sliders | Interação que usuário leigo espera para posicionar PiP/overlay (SupremoCut já tem PiP multicam) | Overlay HTML/SVG absoluto sobre o `@remotion/player`; eventos de mouse escrevem keyframes de x/y/scale/rotation | M |

### C. Corte e edição inteligente (automação)

| Funcionalidade | Origem | O que faz | Por que importa aqui | Como implementar no nosso stack | Esforço |
|---|---|---|---|---|---|
| Detecção de silêncio por pico normalizado em blocos de timebase | auto-editor (`--edit audio`, threshold padrão 0.04) | Pega a amostra de pico mais alta de cada bloco, normaliza, compara a um limiar (fração/%/dB) | Maior economizador de tempo de edição manual possível para um anúncio dublado | Scan de pico/RMS via numpy no motor Python (o VAD do faster-whisper já indica onde há fala) + slider de sensibilidade em dB | M |
| Detecção de imobilidade (motion) | auto-editor (`--edit motion`) | Downscale + escala de cinza + blur gaussiano + diff de frame; abaixo do threshold = "parado" | Útil para telas gravadas/demonstração de produto (cortar trechos genuinamente parados) | Passe paralelo via OpenCV/numpy, combinável com áudio via `(or audio:x motion:y)` | M |
| `--margin` (acolchoamento antes/depois do corte) | auto-editor | Expande cada trecho mantido por N segundos de cada lado antes de cortar | Separa corte automático "robótico" (corta respiração/consoante) de natural | Expandir cada segmento "manter" por N frames de cada lado, exposto como slider único ("respiro entre cortes") | P |
| Corte por palavra/regex sobre transcrição já existente | auto-editor (`--edit word/subtitle/regex`) confirmado como padrão emergente por Rescript e OpenScript | Marca como cortável qualquer trecho cuja legenda bata com uma palavra/expressão | SupremoCut já tem timestamps de palavra (faster-whisper) — Rescript/OpenScript confirmam que "apagar palavra = cortar vídeo" é a lacuna mais concreta hoje | UI de "apagar palavra" na lista de transcrição, gera ripple-delete usando os timestamps já calculados | M |
| Remoção de vícios de linguagem com 1 clique | Rescript + OpenScript (padrão confirmado por 2 projetos independentes) | Lista de filler words ("é", "tipo", "né") + regex sobre o texto transcrito | Ganho de qualidade percebida muito alto para esforço muito baixo em locução dublada/lida | Lista configurável de termos + varredura da transcrição já existente, reaproveitando o pipeline do item acima | P |
| Transição automática só nos cortes gerados por auto-edit | auto-editor (`--transition dissolve:DURATION:MIN-CUT`) | Cross-dissolve curto automaticamente em cada corte que o auto-edit fez, pulando cortes menores que MIN-CUT | Evita jump-cut visível de corte seco em rosto-a-câmera | Ao aplicar lista de cortes automáticos, inserir transição curta (já existe como feature) só nesses pontos | P |
| Expor a curva crua de análise, não só a decisão de corte | auto-editor (`levels`/`info` subcommands) | Devolve o array de métrica por bloco de tempo ANTES do threshold ser aplicado | Permite desenhar linha de threshold arrastável sobre a waveform em vez de botão opaco "auto-cortar" | Motor Python devolve array de volume por frame completo para o front-end sobrepor na visualização de forma de onda já existente | M |
| Ações avançadas com rampa/easing (zoom, drawbox, overlay animável) | auto-editor (`/docs/actions`) | Sistema genérico de rampa+easing aplicável a qualquer trecho casado por um método de edição | Família de recursos "aplique efeito automaticamente ao que o auto-edit encontrou" (ex: acelerar em vez de cortar) | Roadmap de longo prazo — dropdown "Cortar" vs "Acelerar Nx" vs "Silenciar" ao lado do slider de sensibilidade | G |
| Detector de corte de cena robusto a câmera em movimento | PySceneDetect (`AdaptiveDetector`) | Compara score de conteúdo à média móvel local (não a limiar fixo) — filtra falso positivo em pan/tremor de mão | **Alta relevância**: filmagem handheld/UGC é o padrão em anúncio vertical; detector de limiar fixo daria falso positivo constante | Portar a lógica de razão-vs-média-móvel (não precisa da lib inteira) no motor Python para popular marcadores automáticos de corte de plano | M |
| Miniatura automática por cena detectada | PySceneDetect (`save-images`) | Captura frame(s) representativo(s) por plano detectado | Apoio visual para identificar plano na timeline sem abrir cada clipe | Capturar 1 frame por plano via ffmpeg, reaproveitando a capacidade de export PNG já existente | P |
| Detector de fade in/out por brilho absoluto | PySceneDetect (`ThresholdDetector`) | Mede intensidade RGB absoluta (não diferença entre frames) para achar fades, não cortes secos | Anúncios usam fade deliberado entre seções (problema→solução); não sugerir corte de plano ali | Passe leve de brilho médio por frame; sinalizar fade com cor/ícone distinto de corte seco na UI | P |

## Resumo dos vencedores de esforço mínimo

Estes são instaláveis ou aplicáveis quase imediatamente porque o SupremoCut já roda Remotion 4.0.517 (que já libera quase todo pacote `@remotion/*` relevante encontrado nesta pesquisa) e já paga pela API da ElevenLabs:

1. `npx remotion add @remotion/elevenlabs` — Speech-to-Text da ElevenLabs direto no formato `Caption`, zero infraestrutura nova.
2. `npx remotion add @remotion/transitions` — `<TransitionSeries>` com presentations prontas (`slide/fade/wipe/flip/clockWipe`) + `<Overlay>` para light-leak/flash sem alterar a duração da timeline.
3. `npx remotion add @remotion/media` — troca de import quase mecânica para `<Video>`/`<Audio>` com cache de decodificação em memória de graça.
4. `npx remotion add @remotion/effects @remotion/shapes` — blur, light leak e 9 formas SVG prontas, editáveis interativamente no Remotion Studio.
5. `npx remotion add @remotion/sfx` — biblioteca de efeitos sonoros prontos, uso livre, sem custo de licenciamento.
6. `npx remotion add @remotion/paths` / `@remotion/media-utils` / `@remotion/preload` — path animation, waveform client-side, e prefetch de clipe, cada um uma instalação isolada de baixíssimo risco.
7. **Corte por palavra na transcrição já existente** (apagar palavra = cortar vídeo, confirmado como padrão por auto-editor + Rescript + OpenScript) — usa timestamps que o faster-whisper já produz, nenhuma dependência nova.
8. **Corte automático de silêncio via lógica do auto-editor** (Unlicense, domínio público, zero risco de licença) — algoritmo simples de pico normalizado por bloco, testado por anos em produção.

## NÃO transplantar

Coisas vistas nesta pesquisa que considero má ideia para o SupremoCut especificamente, com o motivo:

1. **Compositing por grafo de nós** — Olive, https://github.com/olive-editor/olive/wiki/Nodes. Exigiria expor o conceito de "nó" e "conexão" a um usuário leigo, ou construir um motor de nós inteiro só para escondê-lo atrás de botões simples. O Remotion já resolve o mesmo problema de composição via árvore de componentes React, sem UI de nós.

2. **Color management ponta-a-ponta via OpenColorIO** — Olive (achado via WebSearch sobre o pipeline do Olive). Overkill científico para anúncio vertical visto em celular sem calibração de cor; o material de origem do público-alvo já é majoritariamente Rec.709/sRGB (celular/webcam), não LOG/RAW de câmera profissional.

3. **Scopes de vídeo completos (histograma, waveform, RGB parade, vectorscope)** — Kdenlive e Shotcut, https://docs.kdenlive.org/en/tips_and_tricks/scopes/index.html. Ferramenta de colorista profissional, conceito avançado demais para um usuário que "é leigo em programação"; presets de cor fechados entregam a maior parte do resultado visual em 1 clique, sem exigir leitura de gráfico.

4. **Os 20 blend modes completos, incluindo variantes bitwise e destination-in/out** — Kdenlive, https://docs.kdenlive.org/en/compositing/compositions/composite_and_transform.html. Só cerca de 10 (os que o CSS `mix-blend-mode` já cobre nativamente: multiply, screen, overlay, difference etc.) têm uso recorrente em motion graphics de Reels; o resto é compositing técnico de VFX sem aplicação num anúncio curto.

5. **3-point editing com conceito de Source/Target conectados** — Kdenlive, https://docs.kdenlive.org/en/cutting_and_assembling/editing.html. Fluxo de trabalho de editor profissional de TV/cinema com curva de aprendizado alta; drag-and-drop direto (que o próprio OpenShot usa como alternativa mais simples) é a escolha certa para o público leigo do SupremoCut.

6. **Detecção/mapeamento de proxy nativo de câmera profissional (Sony PXW, GoPro LRV, DJI LRF)** — Kdenlive, https://docs.kdenlive.org/en/tips_and_tricks/useful_info/using_camcorder_proxy_clips.html. O público de anúncio vertical filma majoritariamente com celular/webcam, não câmeras profissionais que gravam proxy nativo em pasta separada.

7. **Adotar o MLT Framework como motor de composição real** — https://github.com/mltframework/mlt. Traria uma dependência C inteira (compilação nativa, empacotamento multiplataforma para Windows) para resolver um problema que o Remotion — que já é a escolha de stack do projeto — já resolve declarativamente em React. Vale só como vocabulário de arquitetura (producer/playlist/tractor), não como dependência real a instalar.

8. **MoviePy como motor de renderização** — https://github.com/Zulko/moviepy. O próprio README admite ser mais lento que FFmpeg direto por causa da ida-e-volta de cada frame via Python/numpy, e issues públicas relatam 12GB+ de RAM e memória não liberada em composições com muitos clipes/textos. Adotar seria regressão de performance frente ao FFmpeg direto que o SupremoCut já usa.

9. **Diarização de speakers como recurso padrão/sempre ativo** — WhisperX + pyannote-audio, https://github.com/m-bain/whisperX. Dependência pesada (PyTorch, aceite de licença/token no Hugging Face) para um caso de uso — múltiplos locutores — que é minoria em anúncio vertical de e-commerce (tipicamente um apresentador só); o próprio README dos autores admite "diarization is far from perfect".

10. **Reescrever a timeline em `<canvas>` via Fabric.js** — designcombo, https://designcombo.dev/framework/core-concepts/timeline-system. Mais performático em tese para milhares de elementos, mas mais difícil de estilizar e depurar que DOM. Só vale considerar se usuários reais reclamarem de lentidão com muitos clipes — não como reescrita preventiva. Recomendação explícita registrada nesta pesquisa: não vale reescrever só por isso.

11. **Motor WebCodecs-first como substituto do Remotion** — Diffusion Studio, https://github.com/diffusionstudio/core. O próprio README deles recomenda o oposto do que seria "copiar": *"se você quer compor vídeo com HTML/React, use Remotion"* — confirmação direta, pela concorrência, de que a escolha de stack do SupremoCut já é a certa para este caso de uso.

12. **Vendorizar ou copiar código literal de projetos AGPL-3.0 ou de licença não-OSI** — OpenChatCut é AGPL-3.0 (https://github.com/0xsline/OpenChatCut); Shotstack Studio SDK é PolyForm Shield (https://github.com/shotstack/shotstack-studio-sdk), que proíbe competir com o produto hospedado da Shotstack. Copyleft de rede (AGPL) obrigaria abrir o código do SupremoCut inteiro; PolyForm Shield proíbe uso comercial competitivo. Seguro estudar a arquitetura e as ideias (o que este relatório faz); arriscado copiar trechos de código literalmente.

13. **Busca semântica via pgvector + Postgres sobre biblioteca de b-roll** — OpenVideo, https://github.com/openvideodev/openvideo. Infraestrutura de servidor errada para um app desktop local single-user; Postgres é overkill operacional para este porte de produto (se algum dia fizer sentido, SQLite com extensão vetorial já bastaria, e mesmo assim é baixa prioridade).

14. **Perseguir arquitetura de plugins/scripting/headless antes de existir demanda real** — ecoando o próprio caso do OpenCut, https://github.com/OpenCut-app/OpenCut. O repositório mais popular desta categoria de pesquisa (~79k estrelas) está preso numa reescrita arquitetural ambiciosa (núcleo Rust, sistema de plugins, modo headless) há tempo suficiente para a versão realmente usável ter sido empurrada para um repositório separado ("classic"). Lição direta de sequenciamento: não trocar uma base estável por ambição de plugin antes de ter uma necessidade concreta.

15. **Tratar o OpenReel Video como dependência a instalar ou confiar** — https://github.com/Augani/openreel-video. O próprio README contém uma seção de token cripto especulativo (endereço de contrato estilo pump.fun) e o projeto se autodescreve como "experimento de desenvolvimento gerenciado por IA" sem revisão humana consistente. Tratar só como catálogo de ideias (ex: audio ducking automático), nunca como código a importar ou dependência a confiar.

16. **hls.js e qualquer lógica de streaming adaptativo** — https://github.com/video-dev/hls.js. Resolve um problema (entrega de vídeo por rede com múltiplos bitrates/DRM/reprodução ao vivo) que simplesmente não existe num editor local que processa arquivos locais via FFmpeg — categoria de ferramenta inteiramente errada para este produto, confirmado só depois de ler o README completo (nada foi descartado sem verificar).
